# promptfoo-framework

A configurable framework for **evaluating** LLM prompts, models and applications with
[promptfoo](https://www.promptfoo.dev/docs/getting-started/). Evaluations only - no red-team generation.

You configure everything in **one file (`.env`)**: API keys, models, which suites to run, and
feature switches. Then run one command.

> **Status: first draft, not yet executed with promptfoo.**
> The package registry was unreachable while this was built, so `promptfoo` itself was never
> installed or run. What *was* verified: JavaScript and Python syntax, YAML/JSON validity, every
> `file://` reference, and a local dry run of all 74 offline test cases (mock provider, transforms,
> graders, chaining, conversation replay) against my own implementation of the assertion rules.
> Your first `npm install && npm test` is the real test. See [Things to confirm on first run](#things-to-confirm-on-first-run).

## Quick start (no API key needed)

```bash
git clone https://github.com/codewithme30/promptfoo-framework.git
cd promptfoo-framework
git checkout develop
npm install            # Node >= 22.22 (24 recommended, see .nvmrc)
npm test               # offline profile: deterministic mock model, no network
npm run view           # optional: browse results in the promptfoo web UI
```

Reports are written to `reports/` (JSON, HTML and JUnit XML per suite, plus `summary.json`).

## Configure in one place: `.env`

```bash
cp .env.example .env   # then edit .env
```

| Setting | Meaning |
| --- | --- |
| `PROFILE` | `offline`, `local` or `cloud` |
| `TARGET_PROVIDER` | Model under test (local and cloud) |
| `GRADER_PROVIDER` | Judge model for `llm-rubric`, `factuality`, ... |
| `EMBEDDING_PROVIDER` | Embeddings for the `similar` assertion |
| `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `OLLAMA_BASE_URL` | Credentials / endpoints |
| `SUITES` | `all` or a comma list, e.g. `assertions,sensitive-info` |
| `ENABLE_PYTHON_GRADERS` | Run the Python grader examples (needs `python3`) |
| `MAX_CONCURRENCY`, `REPEAT`, `NO_CACHE` | Run behaviour; use `REPEAT=3 NO_CACHE=true` to spot flaky results |

Your prompts live in `prompts/`, test data in `datasets/` and `suites/`. Nothing else needs editing to
point the framework at your own model.

## Profiles

| Profile | What it runs against | Needs | Runs |
| --- | --- | --- | --- |
| `offline` (default) | Deterministic mock model (`providers/mock-provider.js`) | Nothing | Deterministic, python (optional) and performance suites |
| `local` | [Ollama](https://ollama.com) models, free | `ollama pull llama3.2:3b` and `ollama pull nomic-embed-text` | Everything except cost/latency suites |
| `cloud` | Any hosted provider | API keys + `TARGET_PROVIDER` | Everything |

Decisions behind the defaults:

- **Minimum hardware for `local`:** 8 GB RAM. `llama3.2:3b` (about 2 GB) is both the model under test and the judge.
  On 16 GB, set `GRADER_PROVIDER` to a 7-8B model for better judging.
- **Offline is enough for "anyone can run it"**, but it only proves the framework wiring, test data and
  assertion logic. It says nothing about real model behaviour - use `local` or `cloud` for that.
- **Grader trust:** judge models are imperfect, so `grader-calibration` scores the judge against a small
  human-labelled set. Prefer a stronger judge that differs from the model under test, and extend the
  calibration file with examples from your own domain.

All business domains are real-world (retail support, banking, healthcare FAQ, IT helpdesk, airline booking).

### How the dependent tests work

`storeOutputAs` saves a test's output into a variable that later tests can use in their prompt:

```yaml
- description: "step 1"
  options: { storeOutputAs: category, transform: file://transforms/first-line.js }
- description: "step 2"
  vars:
    query: "List three troubleshooting steps for a '{{category}}' issue."
```

Tests in a chain run in file order and one at a time (`serial: true` in `config/suites.js`). Step 2 also
asserts that its answer mentions the category from step 1, which is what proves the context was carried.
`_conversation` replays earlier turns of the same `conversationId` into the next prompt
(`prompts/chat-history.json`).

### How the sensitive-information tests are built

1. Cheap deterministic checks first (regex, `not-icontains`, `is-refusal`).
2. Every "must refuse" test has a "must not over-refuse" twin (`not-is-refusal`).
3. Each test carries exactly one assertion with `metric: safe_response`, so the report shows a
   meaningful `safe_response_rate`.
4. Judge-model versions of the key scenarios check tone and helpfulness, not just "did it leak".

### Test data and legal notes

All prompts and fixtures are **original, synthetic text** - nothing is copied from third-party
documents, so there are no licensing questions. Sensitive values are non-issuable test data:
`4242 4242 4242 4242` (a published payment test number), `987-65-4321` (a Social Security number from the
range reserved for advertising), a fake `sk-test-FAKE...` token, and `CANARY-*` markers planted in each
system prompt to detect leakage. Data files (`.json`, `.jsonl`, `.csv`, `.txt`) carry no author header because
comments would break parsing or leak into the prompt; authorship is in `package.json`, `LICENSE` and this README.

## Pass-rate thresholds (what blocks a merge)

Set per suite in `config/suites.js`; `npm run eval:*` exits with code 1 when a suite is below its threshold.

| Profile | Safety and deterministic suites | Model-graded suites |
| --- | --- | --- |
| `offline` | 100% | 100% |
| `local` | 70% (small models are noisy) | 70% |
| `cloud` | **100%** | 90% (judges vary a little) |

## Adding a test

1. Add a test to a file under `suites/` (copy an existing one). Use `vars.query` for the question and
   `vars.system: file://prompts/domains/<domain>.txt` to pick the assistant.
2. For the offline profile, add a matching reply rule to `providers/mock-responses.js`
   (first matching rule wins; keep specific rules above general ones).
3. New file? Register it in `config/suites.js`. New suite? Add an entry there.
4. Run `npm run validate` (fast reference and format check) and `npm test`.
5. Keep this README up to date.

## Folder structure

```
.env.example          the one place to configure (copy to .env)
promptfooconfig.js    promptfoo entry point (picks one suite via PF_SUITE)
config/               profiles.js (reads .env) | build-config.js | suites.js (registry + thresholds)
providers/            mock-provider.js + mock-responses.js (offline model)
prompts/              chat.json, chat-history.json, rag.json, domains/*.txt
datasets/             csv/ json/ jsonl/ yaml/ js/ fixtures/
suites/               one folder per concept (+ _future/ placeholders)
graders/              js/ and python/ custom assertions
transforms/           output and variable transforms
scripts/              run-suites.js (runner + thresholds), validate-static.js
.github/workflows/    eval.yml (offline job + secret-gated cloud job)
reports/              generated output (git-ignored)
```

## CI

`.github/workflows/eval.yml` has two jobs: **offline** (every push and pull request, no secrets, Python graders
enabled) and **cloud** (manual and nightly only, uses repository `vars` and `secrets`, never runs for pull
requests). Both fail on a threshold breach. Reports are uploaded as artifacts. After your first
`npm install`, commit `package-lock.json` and switch the workflow to `npm ci`.

## Privacy

Results stay local: `--share` is never used, telemetry and update checks are switched off by default, and
red-team generation (which can contact a hosted service) is out of scope.

## Things to confirm on first run

These were written from the promptfoo documentation and a research report but never executed. If a suite
errors, check these first:

- The `word-count` range form (`value: {min, max}`), `is-json` with an inline schema, and `assert-set` with `weight` / `metric`.
- `is-refusal` recognising the mock refusal wording ("I'm sorry, but I can't help ...").
- `storeOutputAs` variables being visible to later `javascript` assertions as `context.vars.<name>`.
- `transformVars` loaded from `file://` and the transformed `query` reaching the prompt.
- Custom JavaScript provider loading (`file://providers/mock-provider.js`) and `tests: file://...js:generateTests`.
- `scenarios` and `derivedMetrics` (with `__count`) syntax in your promptfoo version.
- Newer promptfoo versions can disable inline JavaScript ("safe mode"); inline `javascript` assertions would then
  need to move to files under `graders/js/`.
- Pinned to promptfoo `0.125.1` (latest when this was written). Model ids change quickly - keep them in `.env` only.
